# CLAUDE.md

LLM によるコーディングでよくある間違いを減らすための行動ガイドライン。必要に応じて、プロジェクト固有の指示と統合すること。

**トレードオフ:** これらのガイドラインは、速度よりも慎重さを優先する傾向がある。些細なタスクでは、状況に応じて判断すること。

## 1. コーディングの前に考える

**思い込まない。混乱を隠さない。トレードオフを明示する。**

実装する前に:
- 自分の前提を明示的に述べる。不確かなら、質問する。
- 複数の解釈が成り立つ場合は、それらを提示する — 黙って一つを選ばない。
- よりシンプルな方法があれば、そう言う。正当な理由があれば異議を唱える。
- 不明な点があれば、立ち止まる。何が分からないのかを明確にする。質問する。

## 2. シンプルさを優先する

**問題を解決する最小限のコードを。憶測に基づくものは書かない。**

- 求められた以上の機能は作らない。
- 一度しか使わないコードに抽象化を持ち込まない。
- 要求されていない「柔軟性」や「設定可能性」を加えない。
- 起こり得ないシナリオに対するエラーハンドリングは書かない。
- 200 行書いて 50 行で済むなら、書き直す。

自問すること: 「シニアエンジニアならこれを過剰に複雑だと言うだろうか?」 もし「言う」なら、シンプルにする。

## 3. 最小限の変更

**触れるべき箇所だけに触れる。後始末は自分が散らかした分だけ。**

既存コードを編集するときは:
- 隣接するコードやコメント、フォーマットを「改善」しない。
- 壊れていないものをリファクタリングしない。
- 自分なら別のやり方をする場合でも、既存のスタイルに合わせる。
- 無関係なデッドコードに気づいたら、指摘するだけにする — 削除しない。

自分の変更によって不要になったものが生じたときは:
- 「自分の」変更によって使われなくなった import / 変数 / 関数を削除する。
- 元から存在するデッドコードは、求められない限り削除しない。

判定基準: 変更したすべての行は、ユーザーの要求に直接たどれるものでなければならない。

## 4. ゴール駆動の実行

**成功条件を定義する。検証できるまでループする。**

タスクを検証可能なゴールに変換する:
- 「バリデーションを追加する」→「不正な入力に対するテストを書き、それを通す」
- 「バグを直す」→「バグを再現するテストを書き、それを通す」
- 「X をリファクタリングする」→「前後でテストが通ることを保証する」

複数ステップのタスクでは、簡潔な計画を述べる:
1. [ステップ] → 検証: [チェック内容]
2. [ステップ] → 検証: [チェック内容]
3. [ステップ] → 検証: [チェック内容]

強い成功条件があれば、自律的にループできる。弱い条件(「とにかく動かす」)は、絶えず確認を要する。

---

**これらのガイドラインが機能しているサイン:** diff における不要な変更が減る、過剰な複雑さによる書き直しが減る、そして間違いが起きた後ではなく実装の前に確認の質問が出てくる。
