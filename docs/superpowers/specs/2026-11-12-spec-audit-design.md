# spec-audit スキル設計

日付: 2026-11-12

## 目的

仕様・設計資料の網羅性と整合性を点検し、漏れ・矛盾・確認すべき質問を報告ファイルにまとめる Claude Code スキルを作る。
元になったのは、ユーザーが手元で使っていた「仕様の網羅性・整合性点検」プロンプト。今回はこのプロンプトをスキルに移す。

点検だけを行い、対象リポジトリの既存ファイルは一切変更しない。

## 配置

`home/dot_claude/skills/spec-audit/`

| ファイル | 役割 |
|---|---|
| `SKILL.md` | frontmatter、引数の解釈、実行フロー、各 Step の手順、全体ルール |
| `report-template.md` | `coverage-report.md` の章立てと各表のカラム定義 |
| `verifier-prompt.md` | 検証パスのサブエージェントに渡す指示文 |

テンプレートと検証役への指示は、使う段階になってから読む。

frontmatter には `disable-model-invocation: true` を指定し、`/spec-audit` で手動起動したときだけ動くようにする。

## 起動と引数

```
/spec-audit spec=<path...> [req=<path...>] [src=<path...>] [viewpoints="..."] [out=<dir>]
```

| 引数 | 必須 | 内容 |
|---|---|---|
| `spec` | 必須 | 仕様・設計資料 |
| `req` | 任意 | 元になった要件・議事録 |
| `src` | 任意 | 突き合わせに使う実装コード |
| `viewpoints` | 任意 | Step 3 に加えるプロジェクト固有の観点（カンマ区切り） |
| `out` | 任意 | 出力先のルート。既定は `docs/audit` |

`spec`・`req`・`src` には、次のどれでも渡せる。複数の指定や、種類の混在も許可する。

- **ファイル、またはグロブ**
- **ディレクトリ**: 配下を再帰的に読む。
- **URL**: Notion・Confluence・Google Drive・GitHub など、サービスは問わない。読み込みには、そのセッションで使える手段を使う（該当サービスの MCP コネクタ、Web 取得、`gh` などの CLI）。特定のサービスを前提にしない。
  - URL の先が階層構造になっている場合（子ページ、ページツリーなど）は、指定したページとその配下をすべて読む。データベースは全行を読む。
  - 配下のページが50を超える場合は、一覧を示して、続行するかを利用者に確認する。

停止条件は次のとおり。

- `spec` がない場合は、使い方を示して停止する。
- 指定されたパスが存在しない、グロブが何にも一致しない、または URL を読む手段がない・読み込みに失敗した場合は、該当する対象を示して停止する。

対象を自動で探索・推定することはしない。

## 出力

- 初回を含め、常に `<out>/run-N/` に書き出す。N は既存の `run-*` の最大番号に 1 を足した値で、既存のものがなければ 1 とする。
- 前回の run の結果は参照しない。
- 書き込みは `<out>/run-N/` とスナップショット置き場の中だけに限る。

### スナップショット

- 対象の本文は、ローカルファイルも含めてすべて `<スクラッチパッド>/spec-audit/run-N/sources/` にコピーする。Step 1 以降はこのスナップショットだけを読む。
  - スクラッチパッドがない環境では、`$TMPDIR`（未設定なら `/tmp`）の下を使う。
  - リポジトリ内には保存しない。
- スクラッチパッドはセッション単位で消える。後日、資料の本文を再現することはできない。手がかりとして残るのは、`00-inputs.md` に記録した取得日時と最終更新日時だけになる。

### リポジトリ内の出力

| ファイル | 内容 |
|---|---|
| `00-inputs.md` | 引数、対象の一覧（ローカルパス、または URL とページタイトル）、各資料の日付・バージョン・更新履歴、外部ソースの取得日時と最終更新日時（サービスのメタデータ）、スナップショットの保存先、区切り方の宣言 |
| `01-elements.md` | Step 1: 要素一覧 |
| `02-matrices.md` | Step 2: 5つのマトリクスと検出した漏れ |
| `03-viewpoints.md` | Step 3: UC × 観点の表 |
| `04-contradictions.md` | Step 4: 比較記録と矛盾一覧 |
| `05-traceability.md` | Step 5: 突き合わせ結果 |
| `questions.md` | 各 Step で見つけた質問を随時追記する |
| `06-verification.md` | 検証パスの指摘と、その扱い |
| `coverage-report.md` | 最終成果物 |

## 実行フロー

単一のエージェントが順番に実行する。各 Step の結果は中間ファイルに書き出す。次の Step はそのファイルを読み直してから始める。記憶に頼らないので、コンテキストが圧縮されても続きから再開できる。

0. **入力の確定**: 引数を解釈し、対象を列挙する。すべての対象をスナップショットとして保存してから読む。各資料の日付・バージョン・更新履歴を記録する。本文に書かれていない場合は、サービスのメタデータを使う。対象が多い場合は、ユースケース単位で区切って進めることを宣言する。ここまでを `00-inputs.md` に書く。
1. **Step 1: 要素の棚卸し**: 解釈や補完をせず、資料に書かれている要素を抽出する。ID の接頭辞は、アクター `A-`、外部システム `X-`、エンティティ `E-`、状態 `S-`、ユースケース `UC-`、イベント `EV-`、ルール `R-`、用語 `T-` とする。各要素には出典（ファイル名と見出し。複数あればすべて）と確度（confirmed / inferred / TBD）を付ける。ユースケースには、基本フロー・代替フロー・例外フローの有無も記録する。
2. **Step 2: マトリクスによる交差チェック**: 作るマトリクスは次の5つ。
   - 情報 × UC（CRUD）
   - 状態 × イベント
   - アクター × UC
   - UC × フロー種別
   - 外部システム × 連携（失敗時・タイムアウト時・重複受信時）

   行と列は `01-elements.md` の ID から機械的に組み、空きセルも「空」と明記して全セルを埋める。そのうえで、元プロンプトにある漏れのパターンに沿って漏れを列挙する。
3. **Step 3: 横断観点のチェック**: UC × 観点の表を作る。観点は固定の8つに `viewpoints` を加えたもの。各セルは「考慮あり（出典）」「漏れ」「N/A（理由）」のいずれかで埋める。
4. **Step 4: 矛盾の検出**: 出典が複数ある要素について、全記述を並べてから比較する。観点は、用語・定義と値・ルールと条件（範囲の重なりや隙間を含む）・状態遷移・権限・資料間の6つ。比較した要素はすべて記録し、矛盾がなかったものも「比較済・矛盾なし」と残す。矛盾ごとに、該当箇所（両方）、それぞれの記述、どちらが正しいと考えられるか（根拠がなければ「判断不可」）、影響範囲を記録する。資料間で食い違う場合は、日付やバージョンを根拠に記録する。
5. **Step 5: 突き合わせ**: 確認するのは次の4点。
   - 要件にあるのに仕様にない事項
   - 仕様にあるのに実装にない事項
   - 実装にあるのに仕様にない事項
   - 仕様と実装で振る舞いが違う事項

   実施するのは、`req` と `src` が渡された範囲だけ。渡されなかった部分には「対象外（引数なし）」と書く。
6. **検証パス**: 作業の経緯を持たないサブエージェントを1体起動し、`verifier-prompt.md` と、元資料・00〜05 のファイル・`questions.md` のパスを渡す。点検内容は次の3点。
   - 一覧から漏れた要素がないか
   - 根拠のない断定や推測による補完がないか
   - マトリクスや観点表に、確認していないセルがないか

   指摘はメインのエージェントが元資料で確かめる。正しいものだけを各ファイルに反映し、反映しなかったものは理由を `06-verification.md` に記録する。
7. **統合**: `report-template.md` の章立てに従って `coverage-report.md` を作る。

## coverage-report.md の章立て

1. サマリ（漏れと矛盾それぞれの件数、重大なものの上位5件、検証パスで追加・修正した件数）
2. 要素一覧（Step 1）
3. 各マトリクスと検出された漏れ（Step 2）
4. 観点チェックの結果（Step 3）
5. 矛盾一覧（Step 4）
6. 突き合わせ結果（Step 5）
7. 確認が必要な質問リスト（ID / 対象要素 / 種別（漏れ・矛盾・不明点） / 質問 / 重要度（高・中・低） / 判断が必要な理由）

## 全体のルール

- 推測で仕様を補完しない。わからないことは質問リストに入れる。
- 矛盾について、どちらが正しいかを根拠なく決めない。判断できないものは「判断不可」として質問リストに入れる。
- ルールどうしは整合していても、業務として成り立たないと思われる箇所は、懸念として質問リストに入れる。
- 「問題なし」と判断した項目も、何を確認したかを残す。
- 途中で省略しない。
- 各 Step の終わりに、書き出したファイルを読み直して欠けがないことを確認してから次へ進む。
- `<out>/run-N/` とスナップショット置き場の外には書き込まない。
- 外部サービスには読み取り専用でアクセスする。コメント、編集、ページ作成などの書き込み系ツールは呼ばない。
- 出典は「ファイル名＋見出し」、または「ページタイトル＋URL＋見出し」で示す。
- 本文の引用の扱い:
  - 外部ソースの記述は、レポートに本文をそのまま引用せず、要約と該当箇所（URL と見出し）で示す。
  - ローカルファイルの記述は、そのまま引用してよい。

## 検証方法

1. スクラッチパッドに、既知の欠陥を仕込んだテスト用の資料一式を用意する（仕様2ファイル、議事録1ファイル、簡単なコード）。仕込む欠陥は次のとおり。
   - 用語の揺れ（顧客／会員）
   - 数値の食い違い
   - 条件範囲の隙間（10以上／8以下）
   - 抜け出せない状態
   - 作成されるが参照されないエンティティ
   - 議事録で上書きされた決定
   - 実装にあって仕様にない処理
2. サブエージェントにスキルを実行させ、仕込んだ欠陥がすべて `coverage-report.md` で検出されているかを照合する。
3. 対象ファイルが変更されていないこと（実行前後のハッシュ比較）と、`run-N` の採番（2回実行して `run-1`、`run-2` になること）を確認する。
4. スナップショットがスクラッチパッド側にだけ作られ、リポジトリ内に作られていないことを確認する。
5. 検出漏れがあれば SKILL.md を直して再実行する。
6. 外部ソースの読み込みは、使えるコネクタで1件だけ手動で確認する。確認する内容は次のとおり。
   - 配下のページまで読めているか
   - 取得日時が記録されているか
   - レポートで要約による引用になっているか

   外部ソースが変更されていないことはハッシュ比較では確かめられないので、読み取り専用のルールで担保する。

## スコープ外

- 対象の自動探索
- 前回 run との差分比較
- 会話の流れからの自動起動
- サブエージェントによる Step の並列分担
